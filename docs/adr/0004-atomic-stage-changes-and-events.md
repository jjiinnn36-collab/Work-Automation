# ADR-0004 단계 변경을 원자적으로, 모든 변경을 기록으로

- 상태: 채택
- 날짜: 2026-09-16
- 관련: AC-W13, AC-W14, AC-W10

## 맥락

2026-09-15 까지 팝업은 시작할 때 읽은 상태를 메모리에서 바꾸고 **창을 닫을 때** `SaveStatus` 로 썼다.
웹은 요청마다 읽고-바꾸고-썼다. 그래서

1. 팝업이 떠 있는 동안 웹에서 같은 건을 진행하면, 팝업이 닫힐 때 옛 단계 +1 을 써서 **웹의 진행이 사라지거나** 한 번 누른 것이 두 번 진행된 효과가 났다.
2. 팝업이 비정상 종료되면 그날 누른 것이 **모두 사라졌다.**
3. `status` 표는 마지막 값만 가져 **누가 언제 무엇을 눌렀는지** 알 수 없었다. 잘못 눌러 납부로 표시된 건을 추적할 방법이 없었다.

"기한 누락 0건" 에서 가장 위험한 실패가 바로 "잘못 끝남으로 표시되어 조용해지는 것" 이다.

## 결정

- `Store.Advance / Defer / Revert(연도, id, …, 기대단계, 지금, 오늘, 출처)` 를 둔다.
  한 `BEGIN IMMEDIATE` 트랜잭션 안에서 **현재 단계 읽기 → 기대단계와 비교 → 쓰기 → 기록** 을 한다.
- 기대단계는 사용자가 **화면에서 본 단계**다. DB 값과 다르면 `StageConflictException(현재단계)` 로 거절한다.
  마지막 단계에서 진행, 첫 단계에서 되돌리기도 같은 예외로 거절한다.
- 팝업은 누를 때마다 즉시 DB 에 쓴다 (`AlertForm.단계변경` 통로). 거절되면 안내 후 최신 단계로 맞춘다.
  닫을 때 한꺼번에 저장하던 코드는 없앴다.
- 웹 `POST /api/advance|defer|revert` 는 `stage` 를 받는다. 다르면 **409** 와 이유를 돌려준다.
  `stage` 를 안 보내면 확인하지 않는다(옛 화면 호환).
- 보드의 되돌리기도 같은 연산을 쓴다.
- `events` 표에 `시각·연도·id·동작·이전단계·이후단계·출처(팝업/웹/보드)·내용` 을 남긴다.
  동작: 진행, 대기, 되돌리기, 금액, 금액삭제, 첨부, 문서첨부, 첨부삭제. 거절된 누름은 남기지 않는다.

## 결과

- 좋은 점: 동시에 눌러도 정확히 한 번만 진행 (DB-17 에서 6개 스레드로 확인). 누른 즉시 저장.
  언제 누가 바꿨는지 되짚을 수 있다.
- 치르는 값: 팝업이 누를 때마다 DB 를 연다(수 ms). 기록 표는 계속 쌓인다 — 건당 수십 바이트라
  10년 써도 수 MB 수준이라 지우지 않는다.
- `SaveStatus(변경됨)` 는 옛 TSV 이관용으로만 남긴다.
